Architecture & technology — make every box concrete

The public Oscar engineering material establishes the important product pattern — a workflow DSL, scheduled passes, SQS-based processing, FIFO ordering, and an action-processing queue. Oscar does not publicly document every underlying infrastructure choice, so the stack below is an interview-ready concrete implementation, not a claim about Oscar’s private production stack.

Concrete interview stack: React + FastAPI/ECS at the edge; PostgreSQL as the workflow source of truth; SQS for asynchronous work; Redis only for read-heavy, non-authoritative data; EventBridge Scheduler for periodic release; KMS/IAM/Secrets Manager and private networking as cross-cutting controls.
What is the DSL? DSL means domain-specific language: a small declarative language built specifically for campaign workflows. Instead of hard-coding “email → wait 3 days → SMS → wait 3 days → stop” in application code, the campaign stores a versioned graph of decision, action, and wait nodes. The processor is generic and interprets the graph. A simple representation is {nodes:[{id:"email",type:"action",channel:"email",next:"wait1"},{id:"wait1",type:"wait",duration:"3d",next:"responded"},{id:"responded",type:"decision",condition:"client_responded",yes:"done",no:"sms"}]}. That gives operations users a configurable workflow without shipping new backend code for every campaign.
Database

PostgreSQL / RDS

Use a relational database because campaign creation, enrollment, state transitions, idempotency and audit updates need transactions and conditional writes. Store the immutable workflow definition as JSONB, but keep the hot per-member cursor normalized for indexed updates.

Key tables: campaign, workflow_version, campaign_member, outbox_event, idempotency_key, audit_log.

Critical index: (campaign_id, status, next_eligible_at). At large scale, partition the member table and keep analytics queries off the primary.

Async

SQS vs Kafka

Use SQS here. This is fundamentally a worker/task queue: receive, process, acknowledge, retry, DLQ, and backpressure. For the DSL queue, use SQS FIFO with a MessageGroupId that preserves the ordering boundary you actually need (for example, campaign or member).

Use Kafka instead if the platform becomes an enterprise event backbone with many independent consumers, long replay requirements, stream processing, or event-history analytics. Kafka is not needed just to make a worker pool asynchronous.

Cache

Redis / ElastiCache

Yes, but not for authoritative workflow state. Cache immutable/versioned workflow definitions, campaign metadata, provider configuration, and short-lived rate-limit/idempotency data. Never make “is this member already contacted?” a cache-only decision; read the database for correctness.

Queue choice — why two queues?

QueueTypeWhyPayload

AWS documents FIFO queues as the ordering-oriented SQS option and supports MessageGroupId for multiple ordered groups. See SQS FIFO documentation ↗.

Orchestration — two different meanings

Workflow orchestration

The DSL Processor is the application-level orchestrator. It loads the member cursor, evaluates the current node, persists the next cursor, and emits the next action. The WAIT node writes next_eligible_at; it does not hold a worker open for three days.

Infrastructure orchestration

Run API, scheduler and worker containers as ECS services with autoscaling. Scale DSL workers on queue depth / message age, and action workers on action-queue depth plus provider rate limits.

Why not Step Functions per member?

A managed workflow engine is useful for smaller, finite workflows, but a custom DSL keeps campaign semantics in one model and avoids binding millions of member journeys to infrastructure-specific workflow definitions. Mention Step Functions as an alternative only when workflow cardinality and cost are acceptable.

AWS ECS supports rolling and blue/green deployment strategies; blue/green allows validation before production traffic is shifted. See ECS deployment strategies ↗.

Interview problem breakdown

Design Oscar Health’s Campaign Builder

Build an internal tool that lets sales or operations users run campaigns against a selected population, automatically progress each member through a multi-step outreach workflow, wait for responses, and stop safely on failures.

Public-source reconstruction. Oscar has publicly described Campaign Builder as a home-grown engagement and automation platform with a workflow DSL made of decision, action, and wait nodes. The architecture below follows those public engineering disclosures; it is not an internal Oscar specification.

3. Overall architecture

PostgreSQL is the source of truth for status and ownership; the read model/cache only accelerates discovery.

4. Queue strategy — eligibility first, ordering second

Eligibility

Filter first

Visible queue = status=QUEUED AND request.state IN licensed_states(physician). Apply this in the backend before PHI leaves the trusted service.

Fairness

Priority + aging

Urgent work can move ahead, but waiting time increases the effective rank of older normal requests so they cannot starve indefinitely.

Timeliness

SLA urgency

Persist sla_due_at and expose healthy/approaching/breached buckets. Increase urgency as the deadline approaches.

Simple score: effective_score = priority_weight + aging_rate × wait_minutes + sla_urgency, then created_at,id as a deterministic tie-break. The score selects what to show first; it does not authorize a claim.

Start with PostgreSQL queue queries. Add a denormalized queue projection and Redis only when measurement shows read contention. A stale queue is acceptable for discovery, never for assignment.

6. Claim concurrency — two physicians, one ticket

UPDATE consultation_request SET status='CLAIMED', claimed_by=:physician_id, claimed_at=now(), claim_expires_at=now()+interval '5 minutes', version=version+1 WHERE request_id=:request_id AND status='QUEUED' AND version=:expected_version RETURNING *;

A Redis lock can reduce contention, but ownership must be the authoritative transactional state change in PostgreSQL.

7. Timeout and cancellation

Store durable timestamps instead of sleeping workers. A scheduler finds expired leases and conditionally requeues:

UPDATE consultation_request SET status='QUEUED', claimed_by=NULL, claim_expires_at=NULL, version=version+1 WHERE request_id=:request_id AND status='CLAIMED' AND claim_expires_at<now();
Race to avoid: physician clicks Start while the timeout worker runs. If Start changes the row to IN_PROGRESS first, the timeout predicate matches zero rows. If timeout wins, the stale Start gets a conflict and refreshes.

8. State machine + LLD

State transition = (state,event) → nextState. Events: CLAIM, START, RESOLVE, CLOSE, CANCEL, CLAIM_TIMEOUT.
LLD separation: keep the transition function pure; ConsultationOrchestrator owns authorization, repository calls, optimistic concurrency, audit and outbox publication.

9. Real-time dashboard updates

Use SSE for mostly server-to-browser updates or WebSockets for bidirectional sessions. Push only after the DB transaction commits:

{ event:"REQUEST_UPDATED", request_id:"r_456", status:"CLAIMED", queue_version:91 }

Fan out by logical eligibility groups such as state. On reconnect, treat events as hints and refetch from the queue API.

15. Follow-up prompts

Multiple states?

Yes. Treat active licensed states as a set and measure age/SLA per state to avoid hiding local shortages in aggregate metrics.

License changes?

Invalidate eligibility caches and reject new unauthorized claims immediately; apply an explicit policy to already-claimed work.

Stale queue?

Discovery can be stale; assignment cannot. Claim revalidates state, version and authorization.

Consistency?

Counts/position may be eventually consistent; ownership, transitions, authorization and cancel-vs-start must be strongly consistent.

Why not claim on GET?

GET is discovery and can be retried/cached; Claim is a mutation and needs an explicit atomic endpoint.

Testing?

Concurrent claims, duplicate creates, stale versions, timeout-vs-start, license revocation, cross-state access, event duplication and outbox recovery.

60-second interview answer. “I’d keep consultation state and physician ownership in PostgreSQL, enforce active state licensing in the backend, and make Claim a conditional transaction so only one physician can win. The dashboard uses an indexed queue/read model with SSE/WebSockets for low-latency updates. SQS plus a transactional outbox handles notifications and projections; a scheduler handles claim leases and SLA work. Priority, aging and SLA urgency determine ordering. The system is stateless at the API tier, HA at the database layer, idempotent on retries, and auditable with PHI minimized in events and logs.”

1. Understanding the problem

Start exactly like a strong system-design candidate: separate the product contract from the infrastructure. The interesting part is not “send an email.” It is durable, per-member workflow execution with delayed transitions.

Core requirements

Above the line

1) Start a campaign against a selected subset of members. 2) Send an initial email. 3) After 3 days without a response, send SMS. 4) After another 3 days without a response, mark the member unresponsive. 5) Any failed communication or missing contact information ends the campaign for that member.

Below the line

Useful, but defer

Rich visual campaign editing, A/B experiments, advanced journey analytics, next-best-action prioritization, human task routing, many additional channels, and cross-campaign conflict resolution. Mention them after the core design works.

Correctness

Never send the next communication after a member has already responded. Duplicate events and retries must be safe.

Durability

A 3-day wait must survive worker restarts and deployments. Workflow state lives in durable storage.

Scale

The system may need to process hundreds of thousands of enrolled members without dropping or excessively delaying work.

4. High-level design — build it one requirement at a time

Oscar’s public engineering post describes a scheduled campaign pass, a FIFO DSL-processing queue, a DSL processor that evaluates the flowchart, and an action-processing queue that dispatches concrete actions to Oscar services. That becomes our backbone.

Start with the simple pipeline: scheduler → DSL queue → DSL processor → action queue → channel services.

Step A — Start the campaign

1
Create definition. Store the population reference and immutable workflow version.
2
Start command. Mark the campaign RUNNING and create or activate the member enrollment records.
3
Scheduled pass. On its periodic sweep, the scheduler finds enrolled members that are eligible to process and enqueues one message per member.

Step B — Process the member through the DSL

The DSL processor loads the member cursor and repeatedly evaluates nodes. A decision chooses the next branch; an action produces work for the Action Processor; a wait node stores the next eligible time and pauses execution.

Publicly documented architecture, simplified to the interview’s channels. Oscar has described email, SMS, secure messaging, letters, push notifications, and other actions across Campaign Builder.
Why not one giant “campaign workflow” server?Because thousands or millions of members can be independently waiting, sending, and responding. Per-member execution state lets workers scale horizontally while preserving each member’s ordering.

5. Deep dives

Deep dive #1 — Long waits and the WAIT node

Bad: keep a worker process asleep for 3 days. This wastes capacity and is fragile across restarts.

Better: persist next_eligible_at with the workflow cursor and let a periodic scheduler re-enqueue due members. This matches Oscar’s public description of scheduled processing of enrolled entities. The trade-off is bounded timing drift equal to scheduler lag.

Great: make next_eligible_at the semantic contract and monitor the gap between due time and actual processing time. If later requirements demand second-level precision, replace the polling mechanism with a durable delayed-task service without changing the DSL semantics.

Deep dive #2 — FIFO and the large-campaign bottleneck

Oscar’s 2023 engineering post explains that campaign members were required to process in FIFO order, so a single campaign could not simply be split across multiple FIFO queues. Their scaling work included batching SQS receives/deletes and increasing workers; the post reports about 250,000 messages/hour in some periods and lower message age after the change.

Trade-off: FIFO protects ordering but creates a hot-partition risk for one huge campaign. Batching lowers queue transaction pressure, but does not remove the fundamental ordering constraint.

Interview answer: “I would scale workers and batch queue operations first, then revisit the queue-partitioning model only if the business can relax per-campaign ordering.”

Deep dive #3 — Response vs timeout race
The database decides which event wins. Event ordering at the bus is not the correctness boundary.

Use an atomic compare-and-set on (campaign_id, member_id, expected_state, state_version). The response event and timeout event can arrive in either order. Only one can advance the version; the loser becomes a stale no-op.

Deep dive #4 — Delivery failures, retries, and idempotency

Separate communication failure from transport retry. A provider HTTP 500 can be retried without changing campaign state; a confirmed invalid address or permanent delivery failure transitions to CAMPAIGN_ENDED. Every outbound action receives a stable idempotency key such as campaign:member:step:attempt.

At-least-once

Assume duplicate queue delivery and duplicate webhooks.

Dedup

Store event IDs/provider IDs and make state updates conditional.

Outbox

Commit state and the outbound event atomically, then publish asynchronously.

Deep dive #5 — Healthcare security: HIPAA, PHI, BAA

PHI boundary

Keep member identity and workflow state references in queues instead of copying unnecessary PHI into every event. The action service can retrieve the minimum necessary contact data through an authorized internal service immediately before sending.

BAA boundary

A vendor that handles PHI on behalf of a covered entity generally needs the appropriate contractual assurances, commonly through a Business Associate Agreement. A BAA is a governance/control requirement; it does not replace encryption, access control, auditability, or least-privilege design.

Operational controls

SSO/MFA, RBAC, service-to-service authentication, TLS, encryption at rest, managed secrets, redaction of PHI in logs and dead-letter queues, immutable audit trails, consent/suppression checks, and vendor security review.

Deep dive #6 — What happens when multiple campaigns target the same member?

Oscar has publicly described a Next Best Actions framework with priority-action determination, communication phasing, and quotas to reduce conflicting member outreach. Treat this as a production extension beyond the simplified interview workflow: before an action is dispatched, a policy layer can decide whether the communication is currently allowed.

7. State machine + LLD code you can present

State machine — keep it declarative

from enum import Enum

class State(str, Enum):
    ENROLLED = "ENROLLED"
    EMAIL_SENT = "EMAIL_SENT"
    TEXT_SENT = "TEXT_SENT"
    CONTACTED = "CONTACTED"
    UNRESPONSIVE = "UNRESPONSIVE"
    ENDED = "CAMPAIGN_ENDED"

class Event(str, Enum):
    EMAIL_SENT_OK = "EMAIL_SENT_OK"
    EMAIL_FAILED = "EMAIL_FAILED"
    WAIT_DUE = "WAIT_DUE"
    TEXT_SENT_OK = "TEXT_SENT_OK"
    TEXT_FAILED = "TEXT_FAILED"
    CLIENT_RESPONDED = "CLIENT_RESPONDED"

TRANSITIONS = {
    (State.ENROLLED, Event.EMAIL_SENT_OK): State.EMAIL_SENT,
    (State.ENROLLED, Event.EMAIL_FAILED): State.ENDED,
    (State.EMAIL_SENT, Event.CLIENT_RESPONDED): State.CONTACTED,
    (State.EMAIL_SENT, Event.WAIT_DUE): State.TEXT_SENT,
    (State.EMAIL_SENT, Event.EMAIL_FAILED): State.ENDED,
    (State.TEXT_SENT, Event.CLIENT_RESPONDED): State.CONTACTED,
    (State.TEXT_SENT, Event.WAIT_DUE): State.UNRESPONSIVE,
    (State.TEXT_SENT, Event.TEXT_FAILED): State.ENDED,
}

def transition(state: State, event: Event) -> State:
    next_state = TRANSITIONS.get((state, event))
    if next_state is None:
        raise ValueError(f"Invalid transition: {state} + {event}")
    return next_state

# Important production guard:
# the DB update is conditional on the expected state/version.

LLD — separate orchestration from the state machine

class WorkflowOrchestrator:
    def __init__(self, repo, outbox, clock):
        self.repo = repo
        self.outbox = outbox
        self.clock = clock

    def handle(self, cmd):
        e = self.repo.get(cmd.campaign_id, cmd.member_id)
        event = derive_event(e, cmd, self.clock.now())
        next_state = transition(e.state, event)

        # Atomic compare-and-set prevents response/timeout races.
        changed = self.repo.compare_and_set(
            campaign_id=e.campaign_id,
            member_id=e.member_id,
            expected_state=e.state,
            expected_version=e.version,
            next_state=next_state,
        )
        if not changed:
            return  # stale/duplicate event

        self.repo.append_transition(e, next_state, event)

        if next_state == State.TEXT_SENT:
            self.outbox.add(SendAction(
                channel="SMS",
                campaign_id=e.campaign_id,
                member_id=e.member_id,
                idempotency_key=f"{e.campaign_id}:{e.member_id}:sms:1",
            ))

        return next_state
